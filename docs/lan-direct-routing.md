# 内网访问与条件路由排除

## 按所在网络排除 VPN 路由

管理员可在“网络设置 → 按网络排除 VPN 路由”添加规则。每条规则包括“客户端所在网段”和“不接管的目标网段”，两个列表均可填写多个 IPv4 CIDR。例如：

| 客户端所在网段 | 不接管的目标网段 |
| --- | --- |
| `192.168.187.0/24` | `192.168.186.0/24`、`192.168.187.0/24`、`192.168.188.0/24` |

客户端任一链路已连接的物理网卡 IPv4 地址命中左侧列表，就从本次 VPN 路由中排除右侧范围；多条命中规则取并集。规则只匹配物理网卡地址，不使用 VPN 或其他代理的虚拟网卡地址。网段由后台统一下发，不需要客户端环境变量或修改本机配置文件。

这是管理员声明的路由策略。命中的目标使用系统现有路由，IPv4 TCP、UDP、ICMP 均适用，包括原来的跨网段默认网关路径。其余允许目标直接交给 VPN 转发，不再逐 TCP 连接尝试业务端口，也不经过本地透明 TCP 代理。[V2 设计记录](lan-direct-routing-v2-design.md)仅保留历史背景，已不执行。

排除本客户端的 VPN 路由后，其他代理或系统路由仍可能接管流量，因此排除不保证目标一定经物理网关到达。管理员应填写在对应网络中确实可达的目标；不同地点使用相同物理网段也会命中同一规则。匹配期间若目标不可达，客户端不会自动切回 VPN 或重放业务报文。

## 检查与更新时机

规则默认空，未配置时允许目标均走 VPN。保存规则无需重启服务端；支持该功能的客户端在下次心跳同步（通常 30 秒内），也可重连立即获取。旧客户端需要升级才能应用规则。

客户端约每 5 秒读取本机物理接口的 IPv4 地址及链路状态，重新计算匹配规则。这只是本机网络状态检查，不向目标 IP、业务端口或默认网关发送连通性探测，不扫描配置网段，也不在每次访问前等待探测结果。

离开匹配网络、物理链路断开、删除规则或清空规则后，客户端恢复原 VPN 路由；命中规则时重新排除对应范围。规则或网络变化会刷新系统路由，已有 TCP、UDP 等会话可能需要重新建立，包括 WebSocket、SSH 和数据库长连接，不保证长连接无缝迁移。

## 升级与回滚

使用配置分流需将服务端和客户端都升级到 v0.1.20 或更新版本，可先升级服务端，再升级客户端。旧客户端会忽略新规则并保留旧版行为；新版客户端重新连接旧服务端时，缺省规则为空。

新版客户端已移除逐 TCP 探测及其自动直连逻辑。规则为空或未命中时，按原有 VPN 路由转发，不会尝试物理网卡连接业务端口；需要直连的环境应由管理员配置排除规则。

macOS 更新应用后，应在新版应用中断开 VPN，再连接一次。连接时才会校验并更新特权 helper；仅替换应用文件，不保证正在运行的数据面已经更新。

回滚服务端前，应先清空排除规则并等待客户端完成心跳同步。旧服务端的心跳不包含此字段时，新客户端会保留已缓存规则；如果服务端已经回滚，让客户端断开再连接即可重新获取空规则。

## 范围与保护

- VPN 虚拟子网始终保留，包括内置 DNS 使用的 VPN 网关。排除只作用于原本允许的目标范围，不新增 VPN 访问权限。
- 排除比允许网段更细时，会拆分宽路由。例如从 `10.0.0.0/8` 排除 `10.1.0.0/16`，其余地址仍保留 VPN 路由。
- 支持硬件以太网和 Wi-Fi。软件桥、容器 veth 和其他 VPN 接口不作为规则匹配依据。macOS 检查网卡媒体链路，Linux 检查 carrier 与运行状态，Windows 检查接口运行状态；仅保留旧 IPv4 地址的断开网卡不会触发规则。
- 客户端只删除自己添加的路由，不接管或删除其他软件的路由。读取物理网络失败或计算结果超过 1024 条时，保留完整 VPN 路由；系统路由操作失败会记录日志并重试。
- 最多 32 条规则，每个列表为 1～32 个 IPv4 CIDR。支持主机位归一化，拒绝默认路由、IPv6、未指定、回环、链路本地、组播和保留地址范围。未增加 IPv6 条件排除或默认路由全隧道支持。

`https://vpn.xe-flow.com:8443/` 等登录地址和域名解析不由此功能改写。是否访问 `192.168.188.111` 取决于应用使用的目标 IP 或现有 DNS 配置。

## 管理 API 与清理

`GET/PUT /api/v1/admin/network/settings` 顶层使用 `local_route_bypass`，每条规则为 `local_subnets` 与 `excluded_routes`。PUT 缺省该字段保留已有规则，显式 `[]` 清空。

注册响应下发当前完整规则。心跳字段缺省时，客户端保留已有策略以兼容旧服务端；显式空列表撤销排除。规则与允许路由作为同一份策略传递给数据面。

正常断开 VPN 时清理本次添加的 TUN 路由及 DNS，系统原有路由不被接管或删除。本方案不为每条业务连接创建物理 socket、TCP 代理或源地址策略路由。

## 实际环境验收

自动测试覆盖路由区间拆分与恢复、VPN 虚拟子网保留、规则校验、配置热更新、持久化和系统路由操作失败。它们不代替管理员在实际网络中的验收：

1. 配置上表规则，在 `192.168.187.x` 的客户端上确认物理链路已连接。通过原默认网关访问 `192.168.186.x`、`192.168.188.x` 的已知 TCP、UDP 服务，并用 ICMP 验证允许响应的目标。
2. 检查 `ip route get <目标IP>` 或 macOS `route -n get <目标IP>`，结合接口抓包确认目标使用预期系统路径，未进入本客户端的 VPN。其他未排除的允许目标应保持 VPN 路由。
3. 保持 VPN 在线切换到其他物理网络，或拔掉保留静态地址的匹配网卡；约 5 秒后核对排除段已恢复 VPN 路由，再新建业务连接验证访问。
4. 在后台修改、删除及清空规则，确认下次心跳后对应路由变化；检查 VPN 虚拟子网及内置 DNS 仍保留。
5. 切换规则或网络时验证长连接的应用重连能力。匹配网络中目标不通时，确认客户端不会探测目标服务、自动回退或因选路而重放业务报文。
6. 正常断开 VPN 后核对本次 TUN 路由与 DNS 已清理，原有网关、静态路由和其他软件规则保持原样。
