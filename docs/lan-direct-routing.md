# 自动内网直连

客户端已接入 V2 按 TCP 连接选路，解决首次访问和长 socket 一直留在 VPN 的问题。CLI 与桌面端共用该数据面；后台仍维护现有 `allowed_routes`，无需添加新的客户端配置或手工补跨网段路由。[设计动机](lan-direct-routing-v2-design.md)解释了为什么不能只暂存 SYN 并改系统路由。

例如客户端在 `192.168.187.x`，后台配置 `192.168.188.0/24`，应用连接 `192.168.188.111:8443`。客户端会绑定物理网卡及其内网源地址，尝试这个实际 TCP 端口，包括经过默认网关的路径。成功后直接使用这条连接；不通则交给 VPN。新增 `192.168.186.0/24` 或其他网段后，其实际访问的地址也按同样逻辑处理，不扫描整个网段。

## 每个新连接如何选择

1. 服务端下发的网段保持指向 TUN，VPN 虚拟子网始终留在隧道中。客户端接住普通 IPv4 TCP 的首个 SYN，暂不发给 WireGuard。
2. 在最多 800ms 的预算内，经物理出口连接目标业务端口。最多并发尝试 4 个物理出口；成功后保留获胜的真实 socket，立即释放其他尝试。这里没有额外的 ping，也不会探通后关闭再重新连接。
3. 成功后由 smoltcp 处理应用侧的 TCP 握手、确认、重传、窗口和关闭；字节流转发到同一条物理 socket。本机仍经 TUN 分流，直连数据不做 WireGuard 封装，也不经过远端 VPN 节点。TLS 内容保持原样，不解密、不替换证书。
4. 失败或资源不足时放行原始 SYN，固定本次连接走 VPN。SYN 重传不再次尝试内网；不逐个数据包做探测。下一条新连接可重新选择，所以同一 IP 不同端口、不同连接可以同时走直连和 VPN。
5. 已选定的连接不会中途换路。直连断开后，不把已经发送的业务数据重放到 VPN；应用需要重新连接。正常半关闭允许另一方向继续传输，长连接不等待其他会话关闭，也不会因短暂空闲被改路。
6. 后台配置通过既有心跳更新。更新会取消旧配置下尚未完成的尝试，撤销授权会关闭对应的直连会话。每次新连接重新读取当前物理路由；网络切换造成已有 socket 失效时，由应用重连重新判断。

内网不通时，新 TCP 连接可能比直接使用 VPN 多等待最多约 800ms 的拨号预算，外加调度与本机资源清理时间。实际端口立即拒绝会更快失败。此版本不保存跨连接的可达性缓存，因此不会把一个端口或旧网络的成功结果套用到另一条连接上。

## 支持范围与资源限制

- 第一阶段覆盖客户端发起的普通 IPv4 TCP。UDP、ICMP、IPv6、TCP Fast Open、TCP 认证/MPTCP 等不支持的扩展、IP 选项及首次分片流量保持 VPN 路径。已选为直连的流量不会因出现无法解析的 TCP 分片而改发 VPN；此类包丢弃等待 TCP 恢复。出现分片的源/目标地址对会保守停止新增直连，避免同一连接的重传改路。
- 支持硬件以太网和 Wi-Fi；软件桥、容器 veth、其他 VPN 接口不作为物理候选。目标必须在当前配置的 IPv4 网段中，并排除 VPN 子网、回环、多播、链路本地、网络/广播地址等。`/31`、`/32` 可作为精确地址范围；未增加默认路由全隧道支持。
- 每条隧道最多 16 个待选连接、256 个本地 TCP 栈连接。每个直连流的栈与流桥合计约 256KiB 缓冲，TCP 包队列各有 256 包上限。排队满时丢包等待重传，不将已直连流量送往 VPN。
- 尝试历史、连接路径历史、无法重新判定的连接及分片地址对各最多 65,536 项，保留到本条隧道结束。达到历史上限后，新连接保守使用 VPN，已有直连不受影响。保留历史可防止迟到报文或 SYN 重传重新建连、切换路径。已结束的直连五元组至少保留 120 秒关闭保护；应用以不同源端口新建连接不受此限制。
- smoltcp 未完成的应用侧握手在 30 秒后关闭；已建立连接使用 30 秒 TCP keepalive 和 2 小时 TCP 用户超时，不使用短空闲时间回收正常长连接。实际物理连接断开仍需应用重连。
- 连通性只能证明当前地址/端口可达，不能认证站点身份。不同地点使用相同私网 IP 时，应依靠 TLS、SSH 等应用层身份校验。

`https://vpn.xe-flow.com:8443/` 等登录地址和域名解析不由此功能改写。是否访问 `192.168.188.111` 取决于应用使用的目标 IP 或现有 DNS 配置。

## 平台与清理

macOS 使用 `IP_BOUND_IF`，Windows 使用 `IP_UNICAST_IF`，同时绑定物理源 IPv4。Linux 使用 `SO_BINDTODEVICE`，并为真实 socket 的物理源 `/32` → 目标 `/32` 建立独立策略路由，供内核真实 TCP 回包与严格 `rp_filter` 校验使用。该规则不匹配普通应用的 VPN 源地址，不更改 `rp_filter`，也不增加影响所有应用的目标直连路由。

Linux 策略按 socket 引用计数管理；多个连接复用同一源/目标/物理路径时共享规则。取消、失败和正常断开都释放所有权，断开 VPN 时先取消并等待所有拨号/转发，再清理策略、DNS 和本次添加的 TUN 路由。清理失败会报告专用错误，阻止静默重连；系统原有路由不会被接管或删除。策略后端初始化失败只禁用直连，VPN 保持转发。

SIGKILL、断电无法执行用户态清理。Linux 使用的静态策略可能残留，此情况需管理员核对并清理本产品拥有的条目；不能当作正常断开已经完成。实现没有自动清理第三方规则或全局关闭安全检查。

## 实际环境验收

自动测试已覆盖真实 smoltcp 双端握手、大数据传输、半关闭、丢包重传、首连接直连和原 socket 复用、同 IP 双路径、配置撤权、队列背压、取消清理与模拟系统路由事务。它们不操作测试机实际路由，也不代替以下管理员权限验收：

1. 在 `187 → 默认网关 → 188` 的互通环境连接新版客户端，首次打开 `188` 的 SSH/WebSocket/数据库等 TCP 服务。查看 `lan_tcp_dial` debug 日志和物理接口抓包，确认真实 TCP 使用内网源地址，业务包未发送到远端 VPN 节点。保持长连接并验证持续读写。
2. 同一目标开启一个内网可达端口和一个只允许 VPN 的端口，同时连接。确认前者直连、后者经 VPN；两条连接均持续工作。
3. 配置一个新的 `192.168.186.0/24` 范围，访问其中真实在线服务，分别验证默认网关互通与不互通两种结果。无需预先访问其他 IP，也不能因一个 IP 成功便认定整段可达。
4. 保持直连，再撤销该网段权限；心跳同步后应关闭对应直连。切换到外网后重新连接应用，确认自动走 VPN；返回内网再新建连接应恢复直连。
5. Linux 在严格 `rp_filter=1` 下重复上述过程，确认真实 TCP 回包可用。macOS/Windows 同样验证跨默认网关；不能只以路由表候选或 ICMP 成功作为验收通过。
6. 断开 VPN，核对本次 Linux 策略、TUN 路由和 DNS 已清理，原有网关、静态路由及其他软件规则保持不变。

普通 `ip route get <目标IP>` / `route -n get <目标IP>` 仍可能显示 TUN，这是按连接分流的预期行为。应结合 socket 的物理源地址、接口抓包和 `lan_tcp_dial` 日志判定，不能用目标 `/32` 是否改到物理接口作为 V2 验收标准。
