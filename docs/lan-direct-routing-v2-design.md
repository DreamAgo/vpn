# 内网优先：长 TCP 连接的方案调整

状态：V2 已接入客户端，替换 V1 按目标 IP 增加直连路由的实现。本文保留设计动机；实际行为、资源限制与验收步骤以[使用说明](lan-direct-routing.md)为准。实机双站点与 Linux 严格反向路径过滤仍待部署后验证。

## 要解决的问题

V1 在观察到真实访问后探测，再增加目标 `/32` 内网路由。应用的首个 TCP SYN 进入 TUN 时，内核已经选择了 VPN 源 IP；为避免断流，V1 必须等待该目标的旧 TCP 会话结束。WebSocket、SSH 和数据库连接可能长期不结束，因此发现内网可达后仍一直走 VPN。

仅暂存 SYN、修改路由、再放行 SYN 不能解决这个问题：原连接的源地址不会因此重新选择。历史地址缓存或连接 VPN 前预探测只能改善已知目标，不能覆盖首次访问的任意 IP。

## 选择：每条新 TCP 连接独立选择路径

在本机增加透明 TCP 转发层，应用继续使用原目标 IP、端口，不需要配置 SOCKS/HTTP 代理。服务端仍通过现有 `allowed_routes` 下发目标范围。

```text
应用发起新的 TCP 连接
        │
        ▼
本机 TUN：暂存首个 SYN，识别连接与目标权限
        │
        ▼
绑定物理网卡及内网源 IP，尝试连接实际目标端口
        │
        ├─ 成功 → 保留这条真实 TCP socket
        │          本机 TCP 栈承接应用侧连接，双向转发字节
        │          数据经内网网关到目标，不发往 VPN 服务端
        │
        └─ 失败 → 原始 SYN 进入现有 WireGuard 数据面
                   本条连接固定走 VPN
```

这里的内网尝试本身就是后续使用的业务连接，不是探通后关闭、再连接第二次。直连成功必须是**实际 TCP 端口连接成功**；ICMP 成功不能替代 TCP 服务可用性。

本机依然经过 TUN 来接收和分流应用流量，但直连分支不进行 WireGuard 封装，也不经过远端 VPN 节点转发。本地 TCP 转发只处理字节流，不终止 TLS，不替换证书。

应用侧采用固定版本 `smoltcp 0.12.0` 的成熟 TCP 状态机，外层实现有界的包/异步字节流适配器，控制队列、窗口缓冲和连接生命周期。没有自行实现 TCP 重传与拥塞控制。[smoltcp TCP 实现](https://github.com/smoltcp-rs/smoltcp/blob/v0.12.0/src/socket/tcp.rs)

## 长连接行为

| 情况 | V2 行为 |
|---|---|
| 首次访问某个 IP，内网 TCP 端口可达 | 第一次连接就使用内网，无需先建立一条 VPN 长连接 |
| 同一目标已有 VPN 长连接，又发起新连接 | 旧连接继续 VPN；新连接可独立使用内网 |
| 同一 IP，不同端口的内网 ACL 不同 | 各连接按实际端口选择，不能共用一个 IP 的探测结论 |
| WebSocket / SSH 已通过内网建立 | 保持内网连接，无需定期切换 |
| 已建立的内网连接因网络切换而断开 | 关闭本条连接，应用重连时重新选路；不重放已经发送的业务数据 |
| 已有 VPN 连接时回到内网 | 原连接保持，新连接优先内网；不承诺现有 TCP 无缝迁移 |

## 路由与状态管理

- TCP 按连接五元组维护 `待选择 / 内网 / VPN / 关闭` 状态。收到重复 SYN 时复用同一次选择，不能建立重复的内网连接。
- 路径在承接应用侧握手或向 VPN 放行原 SYN 之前确定。一旦交付应用数据，就不能把同一连接再次回退并重放到另一条路径。
- 保留配置网段指向 TUN 的路由，以便同 IP 的不同连接使用不同路径。V1 的全 IP `/32` 路由切换不能与这套机制同时控制同一目标，否则仍会破坏旧连接的源地址和返回路径。
- 第一阶段仅覆盖客户端发起的普通 IPv4 TCP。UDP、ICMP、IPv6、分片/TCP Fast Open 等未经验证的路径继续使用原 WireGuard 转发，不把 TCP 优化描述为所有协议都已直连。
- 物理 socket 必须绑定接口和内网源地址，禁止经当前 TUN 建立“直连”socket。Linux 严格 `rp_filter` 下，不能拿 V1 的 AF_PACKET ICMP 成功代替真实 TCP 建连；需要验证物理源地址的策略路由等平台方案，确保真实 TCP 回包可被内核接收，且不会把应用使用 VPN 源地址的流量改路。不得静默关闭系统全局反向路径过滤。
- 组权限与网段变化仍使用现有心跳。新连接按最新范围检查；权限撤销时关闭受影响的本地直连代理，避免绕过服务端的撤销结果。尝试中的连接带配置版本，旧配置结果不得提交。每次新建连接重新读取物理路径；现有连接不迁移，切换物理网络后由应用重连。
- 软件关闭、异常退出和取消必须统一释放 pending SYN、协议栈 socket、物理 socket、平台旁路资源以及队列，不能留下另一条后台路径继续转发。

## 延迟与资源控制

- 初次内网尝试设一个有界总时限，例如 500–800ms；内网 TCP 成功立即开始承接连接，无需等满时限。
- 内网不可达时，首次连接可能增加一次短等待，再走 VPN。可使用短期失败缓存减少同一网络、同一目标 IP 和端口的重复等待；网络变化或缓存过期后再尝试。失败缓存是优化，不作为永久判定。
- 连接 VPN 前可预热历史目标作为加速措施；任何缓存都不能把一个目标的成功扩展为整个配置网段可达。
- 对待决连接数、并发建连数、SYN 重传合并、每条连接缓冲和全局字节数设上限。超限时在尚未承接握手或交付数据的前提下走 VPN；已经选定路径的连接按背压控制读写，不能无限缓存。
- 本地转发会增加用户态 TCP 处理和数据拷贝成本，需要测吞吐、延迟、CPU 和长时间内存稳定性。不能直接宣称它与纯系统路由的开销相同。

## 实施与验收

代码已完成以下分层并通过自动测试；第 5 项仍需实机验收。失败缓存、连接前预热与性能基准是后续优化，本次未实现。

1. 引入并验证 TCP 包/字节流适配层，先用模拟 TUN 包和本机测试服务验证双向数据、半关闭、RST、重传及背压，不更改用户实际网络。
2. 将现有物理探测能力拆出“创建真实物理 TCP 连接”接口，成功后保留 socket；失败不借用 ICMP 结论。
3. 增加五元组选路模块，接入 TUN/WireGuard 分发；移除对这些 TCP 目标的 V1 全 IP 路由切换。
4. 验证首次未知 IP 的长连接、同 IP 旧 VPN 与新内网连接并存、不同端口独立选择、旧配置尝试取消、权限撤销及 shutdown 清理。
5. 在 macOS、Windows、Linux 实机验证默认网关跨网段互通，Linux 额外验证严格 `rp_filter`。再做网络切换、长连接、多并发和吞吐测试，之后部署新版客户端。

验收核心是：**首次新建的长 TCP 连接可以直接使用可达内网；不需要先等同 IP 的已有 VPN 连接结束。** 这属于客户端数据面改造，不是调整 V1 的探测间隔或 TCP 空闲时间。
