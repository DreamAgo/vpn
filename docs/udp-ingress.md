# 客户端 UDP 接收背压与观测

UDP 接收任务先为应用队列预留容量，再读取 socket。队列满时等待空位，不再因 `try_send` 失败而立即丢弃刚收到的报文。每批最多处理 32 次后主动让出执行机会；WireGuard 状态仍只由转发任务管理。

队列保持 128 个报文槽位。每个复用缓冲区最多 65535 字节，队列容量约 8 MiB，另有接收和消费中使用的缓冲区。不会随持续过载无限增长。socket 的实际接收缓冲区容量受操作系统限制，建立与重连时都会记录。

应用排队时限为 100 ms：从 socket 读取完成开始计时，在转发任务取出时检查，超时的报文回收缓冲区并记为 `expired`，包括 WireGuard 控制报文；握手重传和上层协议需自行恢复。此时限只限制旧报文进入下一处理阶段，不包含内核 socket 缓冲区、网络传输或正在进行的 TUN 写入耗时。持续过载仍可能导致内核丢包，不能将应用队列不满等同于整条链路无丢包。

转发循环约每 10 秒输出一次有流量或拥塞的区间统计，任务退出时输出剩余统计：

| 字段 | 含义 |
| --- | --- |
| `received` | socket 成功读取的报文数量 |
| `expired` | 应用排队超过 100 ms 而主动丢弃的报文数量 |
| `receive_errors` | socket 接收错误数量，不代表内核溢出计数 |
| `backpressure_events` | 等待应用队列空位的次数 |
| `queue_peak` | 已占用或预留队列槽位的峰值，最多 128 |
| `backpressure_max_us` | 等待队列容量的最长时间 |
| `queue_age_max_us` | 出队时观察到的最长应用排队时间，包含过期报文 |
| `processing_max_us` | 单包混淆解码、WireGuard 处理及 TUN 写入的最长总耗时 |
| `queued_packets` | 日志输出时的应用队列长度 |

部署验证应在相同路径、相同方向、相同并发数下对照测试，并同时采集 TCP 重传、UDP 丢包、吞吐、满载延迟、内核 `RcvbufErrors` 和 socket drops。单次吞吐上升不能证明优化成功；应用丢包减少但内核丢包或排队延迟增加，也不能视为问题解决。
